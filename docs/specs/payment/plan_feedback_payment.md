## そもそも「データモデル設計」って何をしているの？

weave は「フォトアルバムをオンラインで編集して製本する」サービスです。
このサービスを動かすには、ユーザーの注文情報・決済情報・写真データなどを**データベース（DB）**に保存する必要があります。

「データモデル設計」とは、**何をどのテーブル（表）のどの列（カラム）に保存するか**を決める作業です。
家を建てる前の設計図のようなもので、ここで判断を間違えると後から直すのが大変になります。

今回のフィードバックは、最初に作ったデータ設計の「仮案」を実際の開発フェーズと照らし合わせて修正した内容です。

## フェーズ構成

| フェーズ | スコープ | 概要 |
|---------|---------|------|
| **Phase 1** | フォトブック編集・保存 | ユーザー登録〜写真アップロード〜アルバム編集〜保存まで。決済機能は含まない |
| **Phase 2-1** | Stripe基本決済 | Checkout Session 発行・Webhook 受信・冪等性保証。`pending_payment` → `paid` 遷移ロジック |
| **Phase 2-2** | 印刷ベンダー連携・発送 | 印刷会社への発注・追跡番号取得・発送通知。`render_queued` 以降のステータス遷移 |

> **なぜ「Phase 1, 2, 3」ではなく「Phase 1, 2-1, 2-2」か**
>
> 決済（2-1）と印刷連携（2-2）はどちらも「注文フロー」に属する密接な機能のため、
> 「Phase 2の前半・後半」として表現しています。
> Phase 3 という番号は将来のスコープ（多言語対応・toBプランなど）のために残します。

## 1. 注文ステータス（OrderStatus）の設計 — Phase 1 のスコープを絞る

### 「ステータス」って何？

注文には「今どの状態にあるか」を示す**ステータス**があります。
宅配便で言えば「集荷済み → 配送中 → 配達完了」のようなものです。

weaveの注文は、最終的に以下の流れをたどります：

```
アルバム編集中
  → 決済ページへ移動
  → 決済完了
  → PDF生成待ち
  → 印刷会社へ発注
  → 製作中
  → 発送
  → 受取完了
```

これを**12個のステータス**として定義します。

### 「enum」とは？

`enum`（イーナム）とは「あらかじめ決めた値しか入れられない型」のことです。
ステータスに「hoge」や「完了」など想定外の値が入らないよう制限するために使います。
信号機が「赤・青・黄」以外の色を取らないようなイメージです。

### フェーズ別の実装方針

全12個のステータスを最初から全部作ることはできますが、**遷移ロジック**（「このステータスからはこのステータスにしか移れない」というルール）を全部実装するのは今の段階では早すぎます。

理由：
- Phase 1 はフォトブック編集・保存が目的。決済機能は含まない
- 印刷会社との連携（発注・追跡）はまだ先の話
- 作りすぎると不要なコードが増えてバグの温床になる

そこで、**enumの定義（名前の列挙）は全12個やっておくが、遷移ロジックはフェーズごとに段階的に実装する**という方針にします。

### Phase 1 で実装するステータス（1つ）

| ステータス | 意味 | いつなる？ |
|-----------|------|-----------|
| `draft` | 編集中・カートに入れる前の状態 | 注文レコード作成時 |

Phase 1 では注文レコードは作成しないため、`draft` ステータスはスキーマ定義のみ行い、遷移ロジックの実装は Phase 2-1 に持ち越します。

### Phase 2-1 で実装する5つのステータスと遷移

| ステータス | 意味 | いつなる？ |
|-----------|------|-----------|
| `pending_payment` | 決済ページへ移動した状態（＝支払い待ち） | Stripe の決済画面を開いたとき |
| `paid` | 決済完了 | Stripe から「支払い成功」の通知が届いたとき |
| `expired` | 決済ページが期限切れ | 30分以内に支払いしなかったとき |
| `cancelled` | キャンセル（決済前） | ユーザーが決済前にキャンセルしたとき |
| `refunded` | 返金済み | 決済後に返金したとき |

**遷移図（どのステータスからどこに移れるか）**

```
draft → pending_payment → paid
                        ↘ expired    （30分タイムアウト）
                        ↘ cancelled  （ユーザーキャンセル）
         （paidから）  → refunded    （返金）
```

### Phase 2-2 以降でenumだけ定義しておく6つ

以下はコードに名前だけ書いておきますが、実際に「このステータスに移る処理」は今は書きません。

| ステータス | 意味 |
|-----------|------|
| `render_queued` | 印刷用PDFの生成待ち |
| `submitted` | 印刷会社へ発注済み |
| `producing` | 製作中 |
| `shipped` | 発送済み |
| `completed` | 受取完了 |
| `failed` | 技術的な失敗 |

## 2. なぜIDが2つ必要なの？（client_reference_id と stripe_checkout_session_id）【Phase 2-1】

### Stripe を使った決済の流れ

```
①ユーザーが「購入する」ボタンを押す
  ↓
②weaveのサーバーが注文レコードをDBに作る（このとき自前のIDを生成）
  ↓
③StripeのAPIを呼んで「決済ページ」を作る
  （このとき②で作ったIDをStripeに渡す = client_reference_id）
  ↓
④ユーザーがStripeの画面でクレジットカード情報を入力して支払う
  ↓
⑤Stripeが weave のサーバーに「支払い完了」を通知する（Webhook）
  （この通知に③で渡したIDが含まれる → これで「どの注文の支払いか」が分かる）
  ↓
⑥weave のサーバーがDBの注文ステータスを「paid」に更新する
```

### 2つのIDの違い

| | `client_reference_id` | `stripe_checkout_session_id` |
|---|---|---|
| 誰が作る？ | weave（自分たち） | Stripe（決済サービス） |
| いつ作る？ | ③の前（注文作成時） | ③のとき（Stripe APIを叩いたとき） |
| 何に使う？ | ⑤のWebhookで「どの注文か」を特定する | 返金や顧客ポータル表示のStripe API操作 |

**なぜ両方必要か：**
- `client_reference_id` がないと、⑤のWebhook通知を受け取ったときに「これは誰の注文か？」が分からない
- `stripe_checkout_session_id` がないと、返金のときに「StripeのどのセッションのPaymentIntentか」が追えない

片方だけでは対応できない場面があるため、両方を保持します。

## 3. 金額（amount_jpy）のロジックは今は作らない【Phase 2-1】

### なぜ？

weave のフォトアルバムの料金体系（ページ数・表紙の種類・送料など）が**まだ決まっていない**ためです。

「料金がまだ決まっていないのにコードを書く」のは危険です。
後で料金体系が変わったときに、そのコードを全部書き直す羽目になります。

### ではどうするか？

- **カラム（列）の定義だけ先に置いておく**（`amount_jpy`・`currency` という列は作る）
- **値を入れるロジックは書かない**（NULLのまま = 空欄のまま）
- Phase 2 で料金体系が確定してから実装する

これは「引き出しは作っておくが、中身はまだ入れない」イメージです。

## 4. 配送先住所はDBに保存しない（個人情報方針）

### どういう情報が「個人情報」か

weaveが扱う主な個人情報：
- ユーザーの**写真**（結婚式・家族の写真など。最も機密性が高い）
- **配送先住所**（名前・住所・電話番号）
- **ユーザー認証情報**（メールアドレスなど）
- **クレジットカード情報**

### なぜ住所をDBに保存しないのか

当初の設計では「Stripe Checkoutが配送先住所を受け取れるので、それをWebhookでもらってDBに保存しよう」と考えていました。

しかし、以下の理由から**自社DBへの保存をやめる**判断をしました：

1. **「個人情報は最小限しか持たない」方針にするため**
   - 写真データには保持期限を設ける予定（例：注文完了後30日で削除）
   - 住所もDBに保存すると「いつ削除するか」が曖昧になってしまう

2. **Stripeが住所を安全に保管してくれているため**
   - Stripe Checkout Session に入力された情報は、Stripe のサーバーに無期限で保存される
   - 必要なときは Stripe の API を呼べばいつでも取得できる
   - わざわざ自分たちのDBにコピーする必要がない

3. **個人情報を「一カ所にまとめる」とセキュリティリスクが増えるため**
   - 自社DBが漏洩した場合のリスクを最小限にするため、個人情報は各専門サービスに委ねる

### 「個人情報は最小限」方針のまとめ

| データ | 保存場所 | 理由 |
|-------|---------|------|
| 写真 | GCS（Google Cloud Storage）に一時保管 | 製本後は削除予定 |
| 配送先住所 | **保存しない**。Stripe APIから都度取得 | 不要なコピーを持たない |
| 名前・メールアドレス | Firebaseに委任（自社DBには保存しない） | Googleのセキュリティに任せる |
| クレジットカード | **保存しない**。Stripeが管理 | PCI DSS（決済セキュリティ基準）に準拠 |

## 5. Webhookの「冪等性」とは？ — stripe_processed_events テーブルの必要性【Phase 2-1】

### 「Webhook」って何？

Webhookとは「何かイベントが起きたときに、外部サービスが自動で通知を送ってくれる仕組み」です。

例：ユーザーがStripeで支払いを完了すると、Stripeが自動的に weave のサーバーに「支払い完了しましたよ」という通知（HTTPリクエスト）を送ります。

```
ユーザーが支払い
  → Stripe が weave サーバーに POST /api/webhook を送る
  → weave がDBの注文ステータスを paid に更新
```

### 「冪等性（べきとうせい）」って何？

冪等性とは「同じ操作を何回やっても結果が変わらない性質」のことです。

例：
- 「100円を支払う」を1回 → 100円引かれる ✅
- 「100円を支払う」を2回間違えて送った → 200円引かれてしまう ❌

Webhookは**同じ通知が2回以上届くことがあります**（ネットワーク障害・タイムアウト時のStripe側の再送など）。
これを適切に処理しないと、「注文ステータスが2回更新される」などのバグが起きます。

### 現在のコードの問題点

現在は「既に paid なら何もしない」というチェックをしていますが、これだけでは不十分です：
- 複数のサーバーが同時に同じWebhookを受信した場合（スケールアウト時）
- 処理中にネットワークエラーが起きた場合

### `stripe_processed_events` テーブルで解決する

すべてのStripe Webhookイベントには一意のID（例：`evt_1abc2def3ghi`）があります。

このIDを「処理済みイベント一覧テーブル」に保存し、**同じIDが来たら処理をスキップする**ことで確実に冪等性を保証します。

```
Webhookが届く
  ↓
stripe_processed_eventsテーブルにこのevent_idが存在する？
  → Yes: 「already processed」として何もしない（スキップ）
  → No:  処理を実行 → event_idをテーブルに保存
```

これはDBの主キー（Primary Key）制約を使うため、たとえ同時に2つのリクエストが来ても片方は必ずエラーになり、二重処理が防げます。

## 6. 追加タスク：個人情報取り扱い方針を文書化する

### なぜ文書化が必要か

「個人情報をどう扱うか」はコードだけでなく**ドキュメントとして明示**しておく必要があります。

理由：
- 将来メンバーが増えたとき、方針が伝わらないとバラバラな実装になる
- 利用規約・プライバシーポリシー作成の基礎資料になる
- どの情報がどこにあるか把握することで、情報漏洩時の対応がしやすくなる

### data_model.md に追加するセクションの内容

以下の4点を記載します：

1. **写真データ**：サービス提供のためにGCSに一時保管。保持期限は今後決定
2. **配送先住所**：自社DBに保存しない。必要時はStripe APIから取得
3. **ユーザー認証情報（名前・メール）**：Firebase Authに委任。自社DBにはIDのみ保持
4. **クレジットカード情報**：Stripe Checkoutが処理。自社では一切保持しない（PCI DSS準拠）
