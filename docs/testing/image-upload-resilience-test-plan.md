# 画像アップロード耐性検証計画

## 1. 目的

Issue #48 配下の画像アップロード耐性検証に向けて、検証対象範囲、代表シナリオ、成功基準、劣化判定基準、必要な計測項目を定義する。

- 親Issue: #48
- 定義Issue: #49
- 計測・ログ追加: #50
- 検証実施: #51

本ドキュメントは、画像アップロード耐性検証の正本とする。

## 2. 現状実装の前提

検証計画は、現時点の実装に合わせて定義する。

| 項目 | 現状 |
| --- | --- |
| プロダクト上の想定最大アップロード数 | 300枚 |
| 主なアップロード導線 | `/album/edit?id={album_id}` の右サイドバー |
| API フロー | `initialize` -> 署名付き URL への `PUT` -> `complete` |
| frontend 受け入れ形式 | JPEG, PNG |
| frontend のファイル上限 | 50MB / 1ファイル |
| frontend のアップロード方式 | 選択ファイルをそのまま並列で送信する。UI 上の並列数指定はない |
| backend の派生生成 | `complete` 実行中に preview / thumbnail を同期生成 |
| media 一覧 API 上限 | `limit` 最大 100 件 |
| media メタデータ保存 | InMemory 実装 |

補足:

- `/album/upload?id={album_id}` は画面として存在するが、現状の本実装で画像アップロードの主導線になっているのはエディタ右サイドバー。
- backend が InMemory 実装のため、検証結果は「現状実装での挙動確認」として扱い、永続化を前提とした保証には使わない。
- プロダクトとしては最大 300 枚のアップロードを想定する。一方で、現状の一覧取得や UI 更新は 100 件制約の影響を受けるため、300 枚ケースでは「受け入れ可能か」と「一覧 UI まで破綻なく追えるか」を分けて評価する。

## 3. 今回の検証対象

今回の耐性検証では、以下を対象とする。

- 現行の editor 画面から行う画像アップロード
- JPEG / PNG の画像アップロード
- 1ファイル 50MB 以下の画像
- 一般ユーザー相当のブラウザ操作
- 枚数、ファイルサイズ、解像度、回線条件、同時アップロード時の挙動
- frontend の体感速度、preview / thumbnail 表示、backend の処理負荷、失敗率

## 4. 今回は対象外

以下は今回の定義と検証対象から外す。

- HEIC / WebP など、現行 frontend で正式サポートしていない形式
- 50MB を超えるファイル
- backend 再起動をまたぐ整合性確認
- 本番インフラを前提とした最終性能保証
- 負荷試験ツールによる API 単体ベンチマーク
- 300枚想定に対する恒久的な UX 保証の確定

| ID | 条件 | 目的 |

| S3 | 100枚 / 良好な Wi-Fi / 一般的なスマホ写真 | 多枚数時の処理耐性確認 |

## 7. 成功基準

各シナリオで最低限、以下を満たすことを成功とする。

### 7.1 共通条件

- `initialize`、`PUT`、`complete` の各段階が進行し、いずれのファイルも 60 秒以上状態変化なしで停止しない
- 完了した画像について preview / thumbnail が表示できる
- ブラウザクラッシュ、タブリロード、画面離脱なしで検証を完了できる
- エラー発生時に `media_id`、失敗段階、エラーメッセージを記録できる

### 7.2 成功率

- S1 から S4 の通常シナリオでは成功率 100%
- S5、S6 の悪条件シナリオでは成功率 95% 以上
- S7、S8 の高枚数シナリオでは API / 処理完了ベースで成功率 99% 以上

### 7.3 UI 条件

- アップロード継続中に、進捗表示が 15 秒以上更新されず停止して見える状態が発生しない
- 写真選択、スクロール、サイドバー操作などの基本操作が 3 秒以上連続して不能にならない
- 一部ファイルが失敗しても、他ファイルの処理が不必要に巻き込まれない

補足:

- 悪条件シナリオでは「全件成功」のみを成功条件にせず、失敗時の切り分けと再現性の確保も評価対象に含める。
- 200 枚以上のケースでは、一覧 UI の整合までを一律成功条件にせず、API と処理完了の到達、記録可能性、UI 上の制約有無を切り分けて評価する。

## 8. 劣化判定基準

以下のいずれかが確認された場合、劣化または要改善と判定する。

### 8.1 定量判定

- 1件あたりの総完了時間で `p95 / p50 >= 3.0` となる
- `complete` 完了後、preview / thumbnail が UI に表示可能になるまで 15 秒超かかるケースが 5% を超える
- アップロード継続中に、進捗表示の無更新区間が 15 秒を超える
- backend CPU 使用率が 85% 超の状態で 60 秒以上継続する
- backend memory 使用率が 85% 超の状態で 60 秒以上継続する

### 8.2 重大失敗

- ブラウザクラッシュ、タブリロード、OOM、プロセス再起動が発生する
- API 5xx や未処理例外により、バッチ全体の進行が止まる
- いずれかのファイルが 60 秒以上状態変化なしで停止し、回復しない
- 7.2 で定義した成功率を下回る

### 8.3 再現性

- 同一条件で 3 回実施したうち 2 回以上、同じ失敗が再現する
- 特定の枚数帯、回線条件、画像条件でのみ継続して同種の失敗が発生する

## 9. 計測したい項目

後続の #50 では、少なくとも以下を取得できる状態を目指す。

### 9.1 frontend

- バッチ開始時刻 / 終了時刻
- 1件ごとの `initialize` 開始 / 完了時刻
- 1件ごとの `PUT` 開始 / 完了時刻
- 1件ごとの `complete` 開始 / 完了時刻
- 1件ごとの総完了時間
- preview / thumbnail が UI に表示可能になるまでの時間
- 成功件数 / 失敗件数 / キャンセル件数
- エラー内容と発生段階
- 実施環境、ブラウザ、回線条件

### 9.2 backend

- `initialize` API 応答時間
- `complete` API 応答時間
- original object の確認時間
- original object のダウンロード時間
- preview / thumbnail 生成時間
- 派生画像 upload 時間
- エラー件数とエラー内訳
- frontend と突合できる識別子

### 9.3 実行環境

- backend CPU 使用率
- backend memory 使用率
- ブラウザ負荷の確認方法
- ネットワーク条件の記録方法
