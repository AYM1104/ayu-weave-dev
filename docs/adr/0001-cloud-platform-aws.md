# ADR 0001: クラウド基盤を AWS に統一する

## ステータス
承認済み

## 日付
2026-04-12

## 背景
本プロジェクトは、3人チームで進めるモノレポ構成の新規開発であり、現時点では実装着手前・仕様整理完了の段階にある。
このタイミングでクラウド前提が複数候補のままだと、設計議論・実装方針・運用手順にブレが出やすく、少人数開発における意思決定コストが増える。
また、AI支援（Claude Code）を活用する前提では、クラウド方針が明示されていない場合に提案が分岐し、レビュー負荷が増える。

## 決定
- このプロジェクトの本番クラウド基盤は AWS に統一する。
- 今後の新規提案・設計・実装は AWS 前提で行う。
- GCP 固有サービスや Firebase 固有依存を新規採用しない。
- 例外が必要な場合は、別ADRで明示的に承認する。
- 本ADRはクラウド「方針」を定めるものであり、個別AWSサービスの詳細選定は後続ADRに委ねる。

## 適用範囲
- 本リポジトリにおける、今後のアプリケーション設計・インフラ設計・運用設計・実装方針。
- 新規追加される仕様書、技術選定メモ、実装コード、運用手順書。

## まだ決めないこと
本ADRでは、以下は未決定とする。
- 認証を Amazon Cognito にするかどうか
- 実行基盤を AWS App Runner / ECS Fargate / Lambda のどれにするか
- DB を Amazon RDS / Aurora のどちらにするか
- IaC を Terraform / OpenTofu / AWS CDK のどれにするか
- メディア処理パイプラインの詳細構成
- 監視基盤の具体構成

## 理由
- 3人チームでの運用負荷を下げるため、クラウド前提を1つに絞り、調査・学習・運用の分散を防ぐ。
- 認識統一のため、設計レビュー時に「どのクラウド前提か」を毎回確認する無駄をなくす。
- Claude Code の判断安定化のため、提案の前提をAWSに固定し、提案内容のばらつきを抑える。
- 開発着手前に方針を確定することで、後戻りコストを最小化する。

## 期待される効果
- 仕様・設計・実装の前提が統一され、意思決定が速くなる。
- ドキュメントと実装の整合性レビューが容易になる。
- AI支援を含む開発フローで、技術提案の一貫性が高まる。

## デメリット
- 特定領域で他クラウドの方が適する場合でも、初期提案の自由度が下がる。
- 既存文書にあるGCP/Firebase前提の記述は、順次見直しが必要になる。

## 検討した代替案
- マルチクラウド前提（AWS/GCP 併用）
  - 却下理由: 3人チームには運用・学習コストが高く、初期フェーズでの複雑性が過大。
- クラウド方針を未確定のまま進行
  - 却下理由: 設計・実装開始後の手戻りが増え、意思決定の遅延が発生しやすい。

## 直後にやること
1. 既存 specs のうち GCP/Firebase 前提の記述を棚卸しし、AWS方針との整合を確認する。
2. 認証・実行基盤・DB・IaC・監視など、未決定項目ごとに後続ADRを起票する。
3. 新規技術提案テンプレートに「本ADRとの差分有無」を確認するチェックを追加する。
