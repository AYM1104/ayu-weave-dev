# docs/CLAUDE.md

## 目的

このファイルは、`docs/` 配下で Claude Code が一貫した判断を行うためのドキュメント運用ルールを定義する。

`docs/` は、このリポジトリにおける仕様、設計判断、運用前提の正本を扱う場所である。
ここで扱う文書は単なる補足メモではなく、実装判断・レビュー判断・変更判断の根拠として機能する。

このファイルは root `CLAUDE.md` を補完する局所ルールであり、矛盾がある場合は root と上位正本を優先する。

---

## このディレクトリの責務

`docs/` で扱うもの:

- 仕様書
- ADR
- 画面・フロー・ユースケース整理
- データモデルや API 契約の設計メモ
- 運用ルール
- 実装判断の前提
- repo 運用に必要な文書

`docs/` で最終責務を持たないもの:

- 実装コードそのもの
- 実装の微細なテクニック
- 一時的な会話メモ
- 根拠のない未来構想
- 未承認事項の既成事実化

ルール:

- docs は「後で読むかもしれないメモ置き場」にしない
- 実装やレビューに効かない曖昧文書を増やしすぎない
- 仕様、判断、未決定事項を区別して書く
- 会話上の思いつきを正本として固定しない

---

## docs の基本原則

- docs はコードの後追い説明ではなく、判断根拠として扱う
- 実装と docs がズレた場合、どちらが正本かを明示する
- 仕様変更をコードだけで閉じない
- 未決定事項は未決定のまま管理する
- 曖昧な期待値を曖昧なまま書かない
- 「やること」「決まっていること」「まだ決めていないこと」を分ける
- 将来案は現在仕様と混在させない

---

## 文書の優先順位

`docs/` 配下では、概ね以下の役割で使い分ける。

1. `docs/adr/*.md`
   - 技術的・構造的な意思決定の記録
2. `docs/specs/**/*.md`
   - プロダクト仕様、フロー、画面、契約、制約
3. その他の補助文書
   - 運用メモ、補足説明、作業支援文書

ルール:

- ADR は「決定とその理由」を記録する
- specs は「どうあるべきか」を記録する
- 補助文書は ADR や specs を置き換えない
- 重要な判断を補助文書だけに閉じ込めない

---

## ADR の扱い

ADR は、長期的に効く技術判断や構造判断を記録するために使う。

ADR に向いているもの:

- クラウド / 実行基盤 / 永続化 / 認証などの重要方針
- 構成の採否
- 大きなトレードオフ判断
- 将来の実装に継続的な制約を与える決定
- 「なぜこの案を採ったか」を残すべきもの

ADR に向いていないもの:

- 単なる実装タスク
- その場限りの微修正
- まだ比較もしていない思いつき
- すぐ消える作業メモ

ADR 記述ルール:

- 何を決めたか
- なぜそう決めたか
- 他案は何だったか
- 何を捨てたか
- どんな影響があるか

を明示する。

ルール:

- ADR で未決定事項を決定済みのように書かない
- ADR が必要な変更をコードだけで進めない
- ADR は結論だけでなく判断理由を残す
- 既存 ADR と矛盾する場合は、黙って上書きせず差分を示す

---

## specs の扱い

specs は、プロダクト仕様や契約の正本として扱う。

specs に向いているもの:

- ユーザーフロー
- 画面仕様
- API 契約
- データモデルの意味
- 制約条件
- エラーケース
- 注文、決済、アップロードなどの主要フロー
- MVP 範囲
- Non-goals

specs に向いていないもの:

- 実装手順の細部
- 開発者の一時作業メモ
- 未承認の将来拡張案
- 根拠の薄い想像仕様

specs 記述ルール:

- 利用者やシステムの振る舞いを明示する
- 「たぶん」「必要なら」などの曖昧な表現を減らす
- 正常系だけでなく、主要な異常系や制約も書く
- UI 表現だけでなく、意味の変化を記録する
- API やデータモデルは名前だけでなく意味を記す

---

## README との役割分担

README は repo の入口として扱う。
README には全体像、目的、最低限の構成説明を置く。

README に向いているもの:

- プロダクト概要
- repo 構成
- セットアップの入口
- MVP / Non-goals の概要
- 参照すべき docs の導線

README に向いていないもの:

- 詳細仕様の本体
- 長い設計判断の全文
- 頻繁に変わる詳細契約の正本

ルール:

- 詳細仕様は specs に置く
- 長期判断は ADR に置く
- README は入口として保つ
- README と specs の重複が増えすぎたら整理する

---

## 未決定事項の書き方

未決定事項は、決定事項と混同しない。

書き分けの原則:

- 決定済み
- 仮説
- 候補
- 保留
- 要承認

を明示する。

ルール:

- 未決定事項を断定口調で書かない
- 仮案を正本へ紛れ込ませない
- 比較中の案は、採用済みのように表現しない
- 「今は決めない」という判断も明示する

推奨表現例:

- 決定: `AWS を前提とする`
- 未決定: `AWS 内の個別サービスは未決定`
- 候補: `候補として A / B を比較中`
- 要承認: `この論点は人間の承認が必要`

---

## 文書更新が必要なケース

以下のような変更がある場合、docs の更新または更新提案を行う。

### specs 更新が必要なケース

- 画面フローの意味が変わる
- API 契約が変わる
- データモデルの意味が変わる
- 入力制約やバリデーション条件が変わる
- 注文、決済、アップロード、プレビューなどの主要体験が変わる
- エラー時の扱いが変わる
- MVP / Non-goals の境界が変わる

### ADR 更新または追加が必要なケース

- 技術方針が変わる
- クラウド / 実行基盤 / 認証 / 永続化 / 監視などの判断が変わる
- 今後の実装に継続的制約を与える決定がある
- 代替案比較が必要な重要論点がある

### README 更新が必要なケース

- repo の入口説明が変わる
- セットアップ導線が変わる
- リポジトリ構成が変わる
- 参照導線が古くなる

## 文体と記述ルール

- 日本語で簡潔に書く
- 1 文 1 意味を意識する
- 抽象語だけで済ませない
- 主語と対象を曖昧にしない
- 誰の責務かを明示する
- 「使いやすい」「柔軟」などの曖昧評価語だけで終わらせない
- 箇条書きで構造化し、読者が判断しやすい形にする
- 実装詳細に寄りすぎず、判断可能な粒度を保つ

避けるもの:

- 会話口調の断片
- 根拠のない断定
- 長いが判断に使えない説明
- 将来妄想の混入
- 実装と無関係な一般論の羅列

---

## ファイル構成の原則

- 文書は責務ごとに分ける
- 1 ファイルに複数論点を詰め込みすぎない
- 逆に細切れにしすぎて追えなくしない
- タイトルで内容が分かる命名にする
- ADR は連番と明確な題名を使う
- specs は対象領域ごとに整理する

ルール:

- 「misc」「notes」「temp」などの曖昧名を正本ファイル名に使わない
- 長大文書になりすぎたら分割を検討する
- 分割しても責務境界が曖昧なら逆効果なので無理に割らない

---

## docs レビュー観点

Claude が docs をレビューするときは、少なくとも以下を確認する。

- 正本として読めるか
- 決定事項と未決定事項が分かれているか
- README / specs / ADR 間で矛盾していないか
- MVP 境界が崩れていないか
- 実装に必要な判断材料が足りているか
- 過剰設計を誘発する書き方になっていないか
- 将来案が現行仕様に混入していないか
- 用語が一貫しているか
- API / データ / フローの意味が曖昧でないか

レビュー結果は以下を分けて示す。

- 問題なし
- 修正推奨
- 要承認
- 今回は保留でよい点

---

## 用語と命名の原則

- 用語は docs 内で統一する
- 同じ意味に複数名を使わない
- 違う意味のものを同じ呼び方にしない
- UI 用語、業務用語、システム用語を混同しない
- 英語表記と日本語表記が混在する場合はどちらを正とするか揃える

ルール:

- 注文、アルバム、レイアウト、テンプレート、アップロード、プレビュー、決済などの基幹用語は統一する
- 一度決めた用語を軽く変更しない
- 用語変更は docs 横断影響を意識する

---

## docs と実装の関係

- docs は実装の説明書ではなく、実装判断の根拠である
- 実装が docs とズレた場合は、どちらを直すべきかを判断する
- docs を更新しないまま実装で意味変更しない
- 実装都合の仮定を docs の事実として書かない

ルール:

- 「コードがそうなっているから仕様もそう」と自動的に扱わない
- 逆に docs が古いなら、差分を示して更新提案する
- docs と実装のどちらが正本か不明なら、勝手に解釈を固定しない

---

## 避けるべき過剰設計

docs は整理のために存在するが、文書体系自体が過剰設計になってはならない。

避けるもの:

- 文書を増やすこと自体が目的化すること
- 3人チームに対して重すぎる文書承認フロー
- 実装前にあらゆる将来案を書き切ろうとすること
- specs / ADR / README / メモの責務重複
- 読まれないルール文書の量産

ルール:

- 実装判断に効く文書を優先する
- まず MVP を進めるために必要な文書を整える
- 理想的な文書体系より、更新され続ける文書体系を優先する

---

## 禁止事項

- 未承認事項を決定済みのように書くこと
- specs と ADR の役割を混同すること
- 重要判断を README や補助メモだけに閉じること
- 実装変更を docs なしで既成事実化すること
- 会話上の仮説を正本に混ぜること
- MVP 外機能を現行仕様に混入させること
- 長いが使えない説明を増やすこと
- 用語の不統一を放置すること
- 将来案と現行仕様を同一粒度で書くこと

---

## Claude の出力ルール

docs 配下で提案・更新・レビューを行うときは、必要に応じて以下を明示する。

- どの文書を更新するか
- なぜその文書更新が必要か
- 決定事項か、未決定事項か
- 実装や他文書への影響
- ADR が必要かどうか
- 今回あえて書かないこと
- 要承認論点

文書変更時は、単に文章を整えるだけでなく、
「この文書が何の判断に使われるか」を意識する。

## このディレクトリでの Claude の基本姿勢

- まず root `CLAUDE.md` を前提にする
- docs の責務を壊さない
- 決定事項と未決定事項を分ける
- 仕様変更をコードだけで閉じさせない
- 重要判断は ADR に寄せる
- 詳細仕様は specs に寄せる
- README は入口として保つ
- 3人チームで更新し続けられる運用を優先する

このディレクトリでは、文書量の多さではなく、
実装・レビュー・意思決定に効くことを最優先にする。
