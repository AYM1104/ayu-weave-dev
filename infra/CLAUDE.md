# infra/CLAUDE.md

## 目的

このファイルは、`infra/` 配下で Claude Code が一貫した判断を行うためのインフラ実装ルールを定義する。

infra は、クラウド構成、環境差分、デプロイ前提、セキュリティ境界、運用基盤の責務を持つ。
このリポジトリではクラウド前提を AWS に統一するが、未承認の個別サービス選定は勝手に確定しない。

このファイルは root `CLAUDE.md` を補完する局所ルールであり、矛盾がある場合は root と ADR を優先する。

---

## このディレクトリの責務

infra で扱うもの:

- AWS 前提の環境設計
- 環境差分の整理
- デプロイ構成
- ネットワーク / 権限 / 秘密情報管理の方針整理
- 実行基盤の定義
- ストレージ / DB / ジョブ / 監視などの構成候補整理
- IaC や環境管理の構造
- 運用上必要な安全策の設計支援

infra で最終責務を持たないもの:

- プロダクト仕様の最終決定
- UI / API の局所都合
- 未承認の AWS 個別サービス確定
- コスト・運用・速度トレードオフの最終決裁
- リリース判断

ルール:

- infra はプロダクト都合の後付け置き場ではない
- 逆に infra の都合だけでプロダクトや API を歪めない
- 構成未確定領域は無理に埋めず、比較案として扱う

---

## 技術方針の大原則

- クラウド前提は AWS に統一する
- Firebase / GCP / Cloud Run / GCS などは新規前提にしない
- 未決定サービスは未決定のまま扱う
- ADR がない重要決定をコードで既成事実化しない
- 3人チーム運用に対して過剰な複雑性を持ち込まない
- 運用できない高度構成より、維持できる単純構成を優先する
- 将来拡張のためだけの重い仕組みを先に入れすぎない

---

## 未決定事項の扱い

以下は、ADR や明示合意がない限り Claude が勝手に確定してはならない。

- 実行基盤の最終採用
- コンテナ運用方式
- DB / ストレージ詳細
- キュー / ジョブ基盤
- CDN / 配信詳細
- 監視 / ログ / 通知構成
- 秘密情報管理方式の詳細
- IaC ツールや運用粒度
- 環境分離戦略の細部
- 可用性 / 性能 / コスト最適化の最終解

ルール:

- 不明なものは「候補」「比較」「保留」として扱う
- 実装は未決定事項に依存しない範囲へ閉じる
- 重要な infra 判断は ADR 提案対象とする
- 仮置きの構成をそのまま正式構成のように書かない

---

## インフラ設計の原則

- 最小構成で始める
- 変更容易性を残す
- しかし抽象化しすぎない
- 環境差分は明示する
- セキュリティ境界を曖昧にしない
- 運用不能な高度化を避ける
- 「本番で困ること」を先に潰し、「将来あるかもしれないこと」を盛り込みすぎない

優先順の目安:

1. 安全性
2. 継続運用性
3. 実装速度
4. コスト最適化
5. 将来拡張性

ただし、この優先順自体が変わる場合は人間判断を要する。

---

## 環境設計の原則

- local / development / staging / production の意味を混同しない
- 環境ごとの差分は意図的に管理する
- 本番専用前提を開発環境へ持ち込みすぎない
- 逆に開発便宜の仮設定を本番へ持ち込まない
- 環境名だけ増やして中身が同じ状態を作らない

ルール:

- 環境追加は理由を明示する
- 環境差分がある場合は、何が異なるかを明確にする
- 環境ごとの secrets や権限差分を曖昧にしない

---

## IaC / 構成管理の原則

- infra 変更は再現可能にする
- 手作業前提を増やしすぎない
- ただし、未決定な運用まで先に固定しない
- 1 つの変更で複数論点を確定しない
- モジュール分割は責務で行い、抽象化のための抽象化を避ける

ルール:

- 使い回しのためだけに過剰抽象化しない
- まだ 1 回しか使っていないものを無理に module 化しない
- 環境差分とサービス差分を同じ抽象で潰しすぎない
- 命名規則、タグ、変数の意味を曖昧にしない

---

## セキュリティの原則

- secrets をコードに埋め込まない
- 固定キーや本番値をサンプルとしても置かない
- 最小権限を意識する
- 権限を広く取りすぎない
- ネットワーク公開範囲を軽く扱わない
- 個人情報、決済関連情報、アップロードファイルの扱いを慎重にする
- セキュリティに関わる変更は「ついで」で進めない

ルール:

- セキュリティ境界変更は要承認として扱う
- 本番で事故る可能性がある設定変更は保守的に扱う
- 一時対応の穴あき設定を恒久化しない

---

## 権限・認可・秘密情報

- IAM 相当の権限設計は最小権限を基本にする
- 秘密情報の参照元を曖昧にしない
- 権限境界を横断する処理を見逃さない
- サービス間の認証 / 認可前提を暗黙にしない

ルール:

- 認証情報を repo に置かない
- 共有しすぎるロールや権限を避ける
- 人間オペレーション依存の秘密管理を増やしすぎない
- ただし最終方式未決定なら、決め打ちで固定しない

---

## ネットワークと公開境界

- 公開範囲を明示する
- インターネット公開が必要なものと不要なものを分ける
- 内部通信前提を曖昧にしない
- 外部 API 通信の前提を明示する
- アップロードや決済導線の経路を軽く扱わない

ルール:

- 何が public で何が private かを明示する
- 内部向け前提を frontend 公開資産へ漏らさない
- 一時開放設定を本番前提として残さない

---

## 可観測性・運用の原則

- 障害時に何が起きたか追える構成を意識する
- ログ、メトリクス、アラートを全無視しない
- ただし MVP 初期から重い監視基盤を作りすぎない
- まずは主要障害を検知できる最小限から始める
- デバッグ不能なブラックボックス化を避ける

ルール:

- ログを出すべき場所と出しすぎてはいけない場所を分ける
- 個人情報や秘密情報をログに出さない
- アラートは数より有効性を優先する
- 監視基盤未決定なら、必要観点だけ整理して保留にしてよい

---

## デプロイと変更管理

- デプロイ単位を曖昧にしない
- ロールバック可能性を意識する
- 破壊的変更を silent に混ぜない
- アプリ変更と infra 変更の依存関係を明示する
- 環境差分の反映漏れを見逃さない

ルール:

- 1 回の変更で構成刷新をやりすぎない
- 変更理由と影響範囲を示す
- DB、権限、ネットワーク、デプロイの変更は特に慎重に扱う
- 手順が必要なものは docs 化を検討する

---

## コストと複雑性

- 使いこなせない高機能構成を避ける
- コスト最適化のために運用不能にしない
- 初期段階で multi-region や過度な冗長化を先回りしすぎない
- 将来の可能性だけで重い基盤を導入しない

ルール:

- コスト削減案は運用負荷とのトレードオフで説明する
- 複雑性追加は、それに見合う明確な利点がある場合だけ提案する
- 3人チームで回せるかを常に確認する

---

## docs / ADR 更新が必要なケース

以下に変更がある場合、infra 実装だけで閉じない。

- クラウド構成の重要判断
- 実行基盤
- 環境分離方針
- secrets / 権限管理方針
- ネットワーク公開境界
- 監視 / ログ / 通知の重要方針
- デプロイ構造
- 永続化戦略
- 非同期基盤や外部連携の重要前提

ルール:

- 長期的影響がある infra 判断は ADR 提案対象とする
- 実装断片だけで構成方針を既成事実化しない
- docs は後追いではなく、判断根拠の記録として扱う

---

## テストと確認観点

infra 変更時は、少なくとも以下を意識する。

- 構文上成立するか
- 依存関係が破綻していないか
- 権限が広すぎないか
- 公開範囲が意図通りか
- 環境差分が破綻していないか
- アプリ側前提と矛盾していないか
- ロールバックや段階反映が必要か
- docs / ADR と整合しているか

Claude は必要に応じて以下を示す。

- 想定影響範囲
- 手動確認が必要な点
- リスクが高い設定
- 保留すべき未決定事項
- 今回見送る高度化

---

## 禁止事項

- AWS 以外のクラウド前提を新規で持ち込むこと
- 未承認の AWS サービス選定を既成事実化すること
- secrets をコードや設定例に埋め込むこと
- 広すぎる権限を安易に許可すること
- 一時的な穴あき設定を恒久化すること
- 過剰な抽象化や module 化
- 3人チームに過重な運用構成
- アプリ要件と無関係な infra 高度化
- 重要判断を ADR なしで固定化すること

---

## Claude の出力ルール

infra で変更提案・実装・レビューを行うときは、必要に応じて以下を明示する。

- 変更対象の構成要素
- 変更理由
- 影響環境
- セキュリティ / 権限影響
- コスト / 運用影響
- docs/ADR 更新要否
- 未決定事項
- 要承認論点
- 今回あえてやらないこと

不確実な構成は断定せず、候補比較や保留論点として扱う。
infra は既成事実化の影響が大きいため、特に保守的に扱う。
