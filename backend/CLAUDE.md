# backend/CLAUDE.md

## 目的

このファイルは、`backend/` 配下で Claude Code が一貫した判断を行うためのバックエンド実装ルールを定義する。

backend は、API、業務ロジック、データ整合、外部連携、非同期処理の責務を持つ。
backend はシステム動作の正本に近い層であり、見た目都合や一時的 UI 事情でロジックを歪めない。

このファイルは root `CLAUDE.md` を補完する局所ルールであり、矛盾がある場合は root と上位正本を優先する。

---

## このディレクトリの責務

backend で扱うもの:

- API エンドポイント
- リクエスト / レスポンス定義
- 業務ルール
- バリデーション
- 永続化処理
- 外部 API 連携
- ジョブ / 非同期処理
- エラーハンドリング
- 認可・権限チェックの実装
- 監査上重要な記録の設計支援

backend で最終責務を持たないもの:

- UI 詳細
- 画面遷移都合のロジック
- 一時的な見せ方調整
- infra サービス選定の最終決定
- プロダクト戦略判断
- リリース判断

ルール:

- backend はシステムの意味を保持する
- frontend の都合だけで業務ロジックを歪めない
- 重要制約を UI に委ねない
- 外部連携や決済完了を楽観的に扱わない

---

## 実装の基本原則

- 業務ロジックを明示的に置く
- ルーティング、業務処理、永続化、外部連携を無秩序に混ぜない
- 役割ごとに責務を分離する
- 小さく変更する
- 副作用のある処理を見えにくくしない
- エラーと成功の境界を曖昧にしない
- 一時しのぎの条件分岐を積み上げない
- 仕様の意味をコードに残す

---

## レイヤ分離の原則

最低限、以下の責務混在を避ける。

- API 層
- 業務ロジック層
- データアクセス層
- 外部連携層
- バックグラウンド処理
- スキーマ / 型定義

ルール:

- API 層に業務ロジックを直書きしすぎない
- DB アクセス詳細を上位層へ漏らしすぎない
- 外部 API の都合をドメイン意味として固定しない
- 一時的実装のために責務境界を崩さない

---

## API 設計原則

- API 契約は明示する
- request / response は意味単位で定義する
- ステータスコードやエラー構造を雑にしない
- 成功時と失敗時の形を一貫させる
- 内部都合のフィールドをそのまま露出しない
- フロントの一時都合でエンドポイントを乱立させない

ルール:

- API 契約を変更したら docs/specs 更新または更新提案を必須とする
- 破壊的変更は承認前提で扱う
- エンドポイント追加時は既存責務との重複を確認する
- 仮レスポンスやモック都合のフィールドを本番契約へ持ち込まない

---

## データモデルの原則

- データモデルは業務上の意味で設計する
- 表示都合だけでモデルを歪めない
- nullable を乱用して整合性を誤魔化さない
- 状態遷移の意味を曖昧にしない
- 監査や再処理に必要な情報を安易に捨てない
- 一度保存した方がよい情報と都度計算でよい情報を区別する

ルール:

- データモデル変更は軽く扱わない
- 意味変更を伴う場合は docs/specs 追従を必須とする
- DB スキーマ変更は将来の移行や既存データ影響を意識する
- 破壊的変更は人間承認前提で扱う

---

## バリデーションの原則

- 入力の妥当性は backend でも保証する
- frontend 側検証を信用しきらない
- 必須、形式、範囲、状態整合を明示的に扱う
- バリデーション失敗の理由を追跡可能にする
- 内部向け理由と外部向けメッセージを混同しない

ルール:

- バリデーションを route ごとにバラバラにしすぎない
- 仕様にある制約を実装で落とさない
- 失敗時に 500 へ逃がさない

---

## エラーハンドリング

- 想定可能な失敗は明示的に扱う
- 例外を握りつぶさない
- 外部 API 失敗、入力不正、権限不足、整合性エラー、内部障害を分ける
- リトライすべき失敗と即時失敗を区別する
- 利用者向けレスポンスと内部ログの粒度を分ける

ルール:

- 外部 API の曖昧な失敗を成功扱いしない
- 決済や注文確定では特に結果を断定しすぎない
- 失敗時の巻き戻しや再試行方針を意識する

---

## 外部連携の原則

このプロダクトでは Stripe と印刷会社 API 連携が重要であるため、特に慎重に扱う。

- 外部連携結果は信用しすぎない
- タイムアウト、重複送信、部分失敗を考慮する
- 冪等性が必要な処理を軽視しない
- 外部 API 依存のフィールドや状態を内部モデルへそのまま漏らしすぎない
- 再実行戦略と失敗時の扱いを曖昧にしない

ルール:

- 注文確定と決済確定を同義で扱わない
- 外部連携完了前に完了扱いへ進めすぎない
- 外部 API 仕様の仮定を docs なしで埋め込まない

---

## 非同期処理 / ジョブの原則

- 時間がかかる処理は同期 API に無理やり押し込まない
- 非同期処理の開始条件と完了条件を明確にする
- リトライ方針を考慮する
- 重複実行リスクを意識する
- 途中失敗時の状態不整合を放置しない

ルール:

- 非同期導入が必要でも、未決定 infra 前提を勝手に固定しない
- 実行基盤未決定なら、責務だけ分離して実装し、基盤依存は閉じ込める
- ジョブ化の必要があるかは、体感速度と整合性で判断する

---

## 認証・認可・権限

- 認証方式未決定の領域は仮決めしない
- ただし権限境界が必要な箇所を見逃さない
- 認可は UI だけに依存しない
- 所有者判定、閲覧可否、更新可否を曖昧にしない
- セキュリティに関わる条件分岐を scattered にしない

ルール:

- 未決定事項に触れる場合は「実装確定」ではなく「考慮点」として扱う
- 仮の認証前提を本番前提のコードへ埋め込まない
- 権限境界に関わる変更は要承認として明示する

---

## 永続化とデータアクセス

- DB アクセスは意味のある単位で行う
- N+1 や無駄な多重アクセスを無視しない
- トランザクションが必要な箇所を見落とさない
- 一貫性が必要な更新を分断しない
- 読み取りと更新の責務を曖昧にしない

ルール:

- ORM / クエリ実装の都合を API 契約へ漏らさない
- スキーマ事情で業務意味を壊さない
- データアクセス最適化は本当に必要な範囲に限定する

---

## docs / specs / ADR 更新が必要なケース

以下に変更がある場合、実装だけで閉じない。

- API 契約
- データモデルの意味
- 状態遷移
- 注文フロー
- 決済フロー
- 外部連携方針
- 認証 / 認可前提
- 非同期処理前提
- 重要な例外ケースの扱い

ルール:

- API またはデータモデル変更は docs/specs 追従を必須とする
- アーキテクチャ上の重要判断は ADR 提案対象とする
- 一時メモやコメントだけで重要方針を残さない

---

## テストと確認観点

backend 変更時は、少なくとも以下を意識する。

- 正常系が成立するか
- 異常系が定義通りに失敗するか
- バリデーションが機能するか
- 権限境界が破れていないか
- 外部連携失敗時に壊れないか
- 冪等性が必要な箇所で重複実行が問題にならないか
- API 契約と実装が一致するか
- 主要フローに回帰がないか

Claude は必要に応じて以下を示す。

- 追加すべきテスト観点
- リスクが高いケース
- 未確認の境界条件
- モックで済ませてよい範囲
- 実運用で確認すべき点

---

## パフォーマンスと保守性

- まず正しさを優先する
- ただし明らかな重さや無駄は放置しない
- 早すぎる最適化を避ける
- 重要経路のボトルネックだけ先に扱う
- 保守不能なトリッキー実装を避ける
- 一時条件分岐の積み上げを技術負債化させない

---

## 禁止事項

- API 層に業務ロジックを過剰に直書きすること
- frontend 都合だけでデータモデルを歪めること
- 契約変更を docs なしで進めること
- 外部 API 失敗を成功として丸めること
- 破壊的変更を承認なしに既成事実化すること
- 認証・権限の仮定を勝手に固定すること
- 一時的回避策を恒久実装にすること
- 例外を握りつぶすこと
- 重要な非同期 / 冪等性論点を無視すること

---

## Claude の出力ルール

backend で変更提案・実装・レビューを行うときは、必要に応じて以下を明示する。

- 変更対象 API / ロジック / モデル
- 変更理由
- 契約影響
- データ影響
- 外部連携影響
- docs/specs/ADR 更新要否
- テスト観点
- 未決定事項
- 今回あえてやらないこと

不確実な構成や infra 前提は断定しない。
重要な設計変更は「提案」と「実装」を分けて扱う。
