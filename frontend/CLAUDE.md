# frontend/CLAUDE.md

## 目的

このファイルは、`frontend/` 配下で Claude Code が一貫した判断を行うためのフロントエンド実装ルールを定義する。

frontend は、ユーザー体験、画面構成、入力補助、表示ロジック、クライアント側状態管理を担当する。
フロントエンドは「見せ方」と「操作体験」の責務を持つが、業務ルールの最終決定や永続化の正本は持たない。

このファイルは root `CLAUDE.md` を補完する局所ルールであり、矛盾がある場合は root と上位正本を優先する。

---

## このディレクトリの責務

frontend で扱うもの:

- 画面設計
- UI コンポーネント
- 画面遷移
- フォーム入力
- バリデーションのうち UX 上必要なもの
- API 呼び出し
- ローディング、空状態、エラー表示
- ユーザー操作体験の改善
- デザインシステムに沿った UI 一貫性
- クライアント側で閉じる軽量状態管理

frontend で最終責務を持たないもの:

- 業務ルールの最終判定
- DB を前提にした整合性保証
- 認可判断の最終実装
- 注文確定ロジックの正本
- 決済の真正な完了判定
- 外部連携の結果保証
- 永続化戦略の決定

ルール:

- 「見た目で防ぐ」ことはしてよいが、「フロントだけで保証する」設計にしない
- 業務上重要な制約は backend 側にも存在する前提で扱う
- フロントの都合で API 契約を暗黙変更しない

---

## 実装方針

- UI は小さく分割する
- 再利用性よりも責務の明確さを優先する
- 早すぎる共通化を避ける
- 1 回しか使わないものは無理に共通化しない
- container 的な責務と presentational な責務を無秩序に混ぜない
- コンポーネント名は役割で命名する
- state は必要最小限に保つ
- derived state を過剰に持たない
- エラー表示、ローディング表示、空状態を省略しない
- フロント都合の複雑な変換は局所に閉じる

---

## ディレクトリ設計の基本原則

- UI コンポーネント
- feature 単位の画面ロジック
- API 通信
- 型定義
- ユーティリティ

を責務で分ける。

ルール:

- ページ固有の実装をグローバル共通に置かない
- 共通 UI と feature 固有 UI を分離する
- API アクセス層と UI コンポーネントを直接密結合させすぎない
- 型置き場を乱立させない
- 命名だけで責務を表せないファイル構成を作らない

---

## UI / UX の原則

- MVP では豪華さよりもわかりやすさを優先する
- 1 画面で扱う責務を増やしすぎない
- ユーザーが今どの段階にいるかを見失わせない
- ファイルアップロード、編集、プレビュー、注文確定、決済導線は特に明確にする
- エラーは「失敗した」だけで終わらせず、次の行動がわかる形にする
- 非同期処理中は連打や二重送信を防ぐ
- 破壊的操作には確認導線を持たせる
- アップロード中、保存中、生成中、決済中などの状態は明示する

---

## 状態管理の原則

- state は最小限に保つ
- サーバー由来データと UI ローカル状態を区別する
- URL に載せるべき状態は URL に寄せる
- 一時 UI 状態をグローバル状態に昇格させすぎない
- フォーム状態、アップロード進捗、モーダル開閉などは必要範囲に閉じる
- 複数画面にまたがる共有が本当に必要な場合だけ共有状態を導入する

禁止に近いもの:

- 1 つのグローバル state に何でも載せる
- サーバー正本データをフロントだけで補正し続ける
- props drilling を嫌って過剰な state 管理を先に導入する
- 一貫性のないキャッシュ戦略を混在させる

---

## API 連携ルール

- API 契約は backend と docs/specs を正本とする
- request / response の型は曖昧に扱わない
- API 失敗時の UI 振る舞いを定義する
- optimistic update は整合性コストに見合う場合だけ使う
- フロントだけの都合でフィールド名や意味を解釈変更しない
- 一時的な変換が必要なら変換箇所を局所化する

ルール:

- API 契約の変更を発見したら、実装だけで吸収せず差分を明示する
- API 契約変更が必要なら backend / docs/specs への影響を必ず示す
- モック都合の仮フィールドを本実装へ持ち込まない

---

## 型の扱い

- 型は省略せず、意味のある粒度で定義する
- `any` の常用を避ける
- UI 専用型、API 型、ドメイン的意味を持つ型を混同しない
- 一時的な nullable / optional の拡大で整合を誤魔化さない
- API response をそのまま全画面にばら撒かず、必要なら境界で整形する

ルール:

- 型の曖昧さで仕様差分を隠さない
- 一見便利でも巨大な共通型を乱用しない
- 意味が異なるものを同一型で済ませない

---

## フォーム実装の原則

- 入力制御は UX 観点で丁寧に行う
- バリデーションメッセージは具体的にする
- 必須・任意を明示する
- フォーム送信中の状態を明示する
- 再送や修正ができる導線を残す
- backend の validation error を適切に表示する

注意点:

- frontend のバリデーションは UX 補助であり、最終保証ではない
- backend 側制約とズレる場合は frontend 側をごまかさず修正する
- 入力補助のために過剰なマジック挙動を入れない

---

## 画像アップロード・編集 UI の原則

このプロダクトでは画像アップロードと簡易編集が中核体験であるため、特に以下を守る。

- アップロード状態を明示する
- 複数画像の扱いを混乱させない
- 編集結果の反映タイミングを明確にする
- 処理中と完了後の違いを視覚的に示す
- 重い処理では応答待ち状態を隠さない
- ユーザーの作業消失リスクを軽視しない

禁止に近いもの:

- アップロード失敗時に原因も再試行手段も出さない
- 保存済みか未保存かが分からない UI
- 編集適用範囲が不明な操作
- 長時間処理で無反応に見える UI

---

## エラーハンドリング

- 失敗を握りつぶさない
- UI に必要な粒度で失敗を表示する
- 再試行可能な失敗と不可能な失敗を分ける
- 認証切れ、権限不足、入力不正、サーバー障害を同一扱いしない
- console に出すだけで終わらせない

ルール:

- 表示メッセージは開発者向け文言をそのまま出さない
- ただし原因把握に必要な情報を消しすぎない
- 想定失敗ケースを UI 上無視しない

---

## パフォーマンスの原則

- 重い処理を画面全体へ波及させない
- 不要な再レンダリングを増やさない
- 巨大コンポーネントを避ける
- 過剰なクライアントサイド処理を持ち込まない
- 初期表示、アップロード、プレビュー、編集体験を優先して最適化する

ルール:

- 体感差の小さい微最適化を先にやらない
- MVP 段階で複雑な最適化機構を先に入れない
- まずはボトルネックが明確な箇所だけ対処する

---

## アクセシビリティと品質

- ボタン、入力、ラベル、エラー表示の意味を明確にする
- キーボード操作を破壊しない
- 視覚依存だけの表現に寄りすぎない
- クリック可能要素を曖昧にしない
- disabled 状態や loading 状態を見た目だけにしない

MVP でも最低限守るもの:

- ラベルの明確さ
- フォーカス移動の破綻防止
- 主要操作の視認性
- エラー位置の分かりやすさ

---

## docs / specs 更新が必要なケース

以下に変更がある場合、実装だけで閉じない。

- 画面フローの意味
- ユーザー操作手順
- 表示すべき主要状態
- 入力制約
- エラー時 UX
- API 依存前提
- レイアウト生成やプレビューの体験要件

ルール:

- UI の見た目だけの微修正を除き、体験意味が変わるなら docs/specs への反映を検討する
- backend 契約変更にフロントだけで追随して終わらせない

---

## テストと確認観点

frontend 変更時は、少なくとも以下を意識する。

- 表示が壊れていないか
- ローディング、成功、失敗、空状態が成立しているか
- フォーム入力と送信が成立するか
- API エラー時に破綻しないか
- 二重送信や誤操作が起きやすくなっていないか
- 主要フローを阻害していないか

Claude は必要に応じて以下を示す。

- 確認すべき画面
- 再現手順
- 想定正常系
- 想定異常系
- 未確認リスク

---

## 禁止事項

- frontend だけで業務ルールを確定すること
- backend 契約を暗黙変更として扱うこと
- API 差分を型の緩和で誤魔化すこと
- 一時 UI 事情を全体設計へ持ち込むこと
- 早すぎる共通化
- 巨大コンポーネント化
- 無関係な UI 修正を同一変更に混ぜること
- 重い state 管理を必要前に導入すること
- UX 上重要な失敗ケースを未処理のままにすること

---

## Claude の出力ルール

frontend で変更提案・実装・レビューを行うときは、必要に応じて以下を明示する。

- 変更対象画面 / コンポーネント
- 変更理由
- 体験上の影響
- backend / docs/specs への影響
- 状態追加や型変更の有無
- テスト / 動作確認観点
- 今回あえてやらないこと

不確実な仕様は UI 上の思いつきで確定しない。
必要なら「仮案」「確認事項」として分離する。
