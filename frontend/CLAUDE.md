# frontend/CLAUDE.md

## 目的

このファイルは、`frontend/` 配下で Claude Code が一貫した判断を行うための最小ルールを定義する。

frontend は、画面表示、画面遷移、入力体験、クライアント側状態管理の責務を持つ。
業務ルールの最終決定や整合性保証は backend 側を正本とする。

このファイルは root `CLAUDE.md` を補完する局所ルールであり、矛盾がある場合は root を優先する。

---

## このディレクトリの責務

frontend で扱うもの:

- 画面表示
- 画面遷移
- UI コンポーネント
- フォーム入力
- API 呼び出し
- ローディング / エラー / 空状態の表示
- クライアント側状態管理

frontend で最終責務を持たないもの:

- 業務ルールの最終判定
- 認可判断の最終実装
- DB 整合性の保証
- 注文確定や決済完了の真正判定
- 外部連携の結果保証

ルール:

- frontend の都合だけで API 契約を歪めない
- 重要制約を frontend だけで保証しない
- backend が正本である前提を崩さない

## ディレクトリ配置ルール

### `app/` に置くもの

`app/` には、App Router のルーティングとページ表示の組み立てを置く。

例:
- `page.tsx`
- `layout.tsx`
- ルート単位のディレクトリ

ルール:
- `app/` はページ入口として使う
- 画面全体の組み立てはよいが、feature 固有ロジックを溜め込みすぎない
- 重い UI ロジックや状態管理を `app/` に直書きしない

### `features/` に置くもの

`features/<feature>/` には、その機能に閉じる UI ロジックを置く。

例:
- feature 固有コンポーネント
- feature 固有 hook
- feature 固有 schema / 型
- feature 固有 API 呼び出し補助

ルール:
- 機能に閉じる実装は `features/` に置く
- 他 feature の内部実装へ直接依存しすぎない
- 1 回しか使わない UI を無理に共通化しない

### `components/` に置くもの

`components/` には、複数 feature から再利用される共通 UI を置く。

例:
- Button
- Modal
- Dialog
- 汎用フォーム部品

ルール:
- feature 固有 UI を安易に `components/` へ出さない
- 共通化のための共通化をしない
- 画面固有コンポーネントを共通扱いしない

### `hooks/` に置くもの

`hooks/` には、複数 feature や複数画面で再利用する共通 hook を置く。

ルール:
- feature 専用 hook は feature 配下に置く
- 一度しか使っていない hook を安易に共通化しない

### `lib/` に置くもの

`lib/` には、共通 utility や API client などの基盤コードを置く。

ルール:
- UI ロジックを `lib/` に入れない
- feature 固有処理を `lib/` に逃がしすぎない

### `store/` に置くもの

`store/` には、複数 feature または複数ページで共有が必要な state だけを置く。

ルール:
- 一時的な画面 state を安易に global state にしない
- フォーム入力やモーダル開閉などは、必要なら feature や page に閉じる
- 何でも store に載せない

### `types/` に置くもの

`types/` には、複数箇所で使う共通型を置く。

ルール:
- feature 固有型は feature 配下に置く
- API 型、UI 型、共通型を無理に一つへまとめない

## 実装の基本原則

- UI は小さく分割する
- `app/` は薄く保つ
- feature ロジックは feature 配下に寄せる
- state は必要最小限にする
- ローディング、エラー、空状態を省略しない
- 二重送信や無反応に見える状態を避ける
- frontend 都合だけで API 契約を解釈変更しない

---

## Server / Client Component の原則

- Client Component は必要な場所だけに限定する
- 画面全体を安易に Client Component にしない
- ブラウザ依存の状態やイベント処理が必要な部分だけを Client にする
- データ取得や静的表示で済む部分は、可能なら Server 側に寄せる

---

## 状態管理の原則

- state は最小限に保つ
- URL に載せるべき状態は URL に寄せる
- 一時 UI 状態を global state に昇格させすぎない
- サーバー正本データを frontend 側だけで補正し続けない

---

## docs 更新が必要なケース

以下に変更がある場合、実装だけで閉じない。

- 画面フローの意味
- ユーザー操作手順
- 入力制約
- 表示すべき主要状態
- API 依存前提
- エラー時 UX

---

## テストと確認観点

frontend 変更時は、少なくとも以下を意識する。

- 表示が壊れていないか
- ローディング、成功、失敗、空状態が成立しているか
- フォーム入力と送信が成立するか
- API エラー時に破綻しないか
- 二重送信や誤操作が起きやすくなっていないか

---

## 禁止事項

- frontend だけで業務ルールを確定すること
- `app/` に feature ロジックを溜め込みすぎること
- feature 固有 UI を安易に `components/` へ出すこと
- 何でも `store/` に載せること
- API 差分を型の緩和で誤魔化すこと
- 無関係な UI 修正を同じ変更に混ぜること

---

## Claude の出力ルール

frontend で提案・実装・レビューを行うときは、必要に応じて以下を明示する。

- 変更対象画面 / feature
- 変更理由
- 体験上の影響
- API / docs への影響
- 状態追加の有無
- テスト / 動作確認観点
- 今回あえてやらないこと
